# 0007 固件存储布局与 OTA

## 决策

### 分区

4 MB flash 分为互相独立的几类分区：

| 内容 | 分区 | 写入者 |
|---|---|---|
| 固件 | 两个应用分区 `ota_0`、`ota_1`，加 `otadata` | 首次烧录、OTA |
| 配对参数 | 出厂分区 `fctry` | 生产时烧录，固件只读 |
| 运行时数据 | `nvs` | 固件，含 Matter 配网信息、Wi-Fi 凭据、节点设置 |

### 配对参数

- 配对口令、discriminator 和 SPAKE2+ 验证数据存放在 `fctry`，由 esp-matter 的 mfg 工具按设备生成，同时生成配对二维码和手动配对码。
- 固件使用 ESP32 Factory Data Provider 读取 `fctry`。发布版关闭测试配对参数，固件镜像中不含任何配对口令，同一份固件可用于所有设备；开发测试时允许打开测试配对参数（SDK 内置的公开测试值），这样的固件不得用于发布。
- 每台设备使用不同的口令和 discriminator。
- 设备证书由用户自行保存，项目不做规定；厂商 ID、产品 ID、序列号等设备信息的来源同样不做规定，由使用者提供。开发阶段使用测试值。

### OTA

- 固件通过 Matter OTA 升级，写入当前未运行的那个应用分区，校验通过后切换启动分区。
- OTA 只修改 `ota_0`、`ota_1` 和 `otadata`，不写入 `fctry` 和 `nvs`。升级后配对参数、配网信息和节点设置全部保留，节点不需要重新配网。
- 恢复出厂设置只清除 `nvs`，不清除 `fctry`，也不改变当前固件版本。
- 新版本固件必须能读取旧版本写入 `nvs` 的数据。
- 开启自动回退：OTA 后新固件首次启动处于“待验证”状态，自检通过才确认有效；确认之前发生重启（崩溃、看门狗复位、断电）或自检超时，引导程序退回旧固件。
- 自检以硬件为依据：风扇 PWM 输出、状态 LED、按键的硬件初始化成功并已启用，Matter 协议栈和蓝牙启动成功，才确认固件有效。自检不依赖 Wi-Fi 连接和网络状态。
- 新固件确认有效之前，不迁移 `nvs` 的数据格式，保证回退后的旧固件仍能读取 `nvs`。
- 回退后，旧固件把被回退固件的软件版本号记录在 `nvs` 中，只保留最近一次回退的记录。
- 只接受比当前固件和最近一次回退的固件都更新的固件：新固件的软件版本号必须同时大于当前固件和被回退固件的软件版本号，否则在收到升级提议时直接拒绝，不下载。
- 软件版本号为 32 位无符号整数，取构建时的本地时间，格式为 YYMMDDHH（年取后两位，精确到小时，共八位十进制数，如 26111116），随构建时间自然递增。
- 镜像完整性依赖 ESP-IDF 应用镜像自带的校验和与 SHA-256：下载完成时校验，通过才切换启动分区；引导程序每次启动再校验一次。不使用固件签名（不开启安全启动和应用签名），设备端也不校验 Matter OTA 文件头里的摘要。

## 依据

- 不同设备共用配对口令会让任何持有二维码的人都能添加其他设备，Matter 要求每台设备的口令唯一。口令放在固件里则无法做到同一份固件用于多台设备。
- Matter 控制器通过 OTA 升级设备，设备需要同时容纳旧固件和新固件，并在升级失败时仍能启动旧固件，所以使用两个应用分区。
- 配对参数和运行时数据分属不同分区，是因为二者的写入者和生命周期不同：前者在生产时写入、之后只读，后者由固件在运行中改写，并会被恢复出厂设置清除。
- 4 MB flash 能否放下两个应用分区的结论见本 ADR 的影响。
- 升级只能往前走：回退过的固件，以及比它更旧的固件，都不应该再被装上；软件版本号随升级提议一起到达，在下载之前就能判断，避免白下载一遍。
- 版本号取构建时间，新旧可以直接比较，不需要人工维护递增；Matter 的软件版本号是 32 位无符号整数，上限 4294967295，YYYYMMDDHHMM 共十二位，放不下，所以年份只取后两位、精度只到小时。
- 镜像校验只能发现损坏的镜像，发现不了校验通过但启动后运行异常的固件；没有回退时这样的固件只能通过烧录插座恢复，设备装在风扇上，现场不一定方便。
- 自检以硬件为依据而不看网络：路由器断开外网或重启期间系统仍应正常运行（[F-001](../prd.md#f-001)），失联保持（[F-009](../prd.md#f-009)）；以 Wi-Fi 连上为标准，升级时碰上路由器重启就会把好固件错误回退。
- ESP-IDF 镜像哈希能发现下载损坏和截断；镜像通过 Matter 的加密、带认证的会话传输，传输中途被篡改会在这一层被发现。

## 备选方案

### 编译时把配对口令写进固件（未采纳）

同一批设备共用口令，不满足每台设备口令唯一的要求，换口令需要重新编译固件。

### 配对参数放在 `nvs`（未采纳）

恢复出厂设置会清除 `nvs`，设备将失去配对口令。固件的运行时写入也可能损坏出厂数据。

### 只保留一个应用分区，OTA 时原地覆盖（未采纳）

升级中断电会使设备无法启动，只能用烧录插座重新烧录。

### 通过 Wi-Fi 自行实现 OTA，不走 Matter（未采纳）

需要自建固件分发和校验流程，控制器侧也没有统一入口。

### 不开启自动回退（未采纳）

校验通过但运行异常的新固件会使设备一直停在坏固件上，只能用烧录插座重新烧录。

### 以 Wi-Fi 连接成功作为自检标准（未采纳）

升级时路由器断开或重启，会把正常的新固件错误回退，且与路由器断开期间系统仍应正常运行的要求冲突。

## 影响

- 生产时每台设备需要单独烧录一份 `fctry` 镜像，并保管对应的二维码和手动配对码。
- 两个应用分区各占约 1.9 MB，当前含全部 Matter 端点的原型固件使用其中约 81%，加入同步、持久化等功能后需要再确认是否放得下，放不下时需要缩减功能或改用更大的 flash。
- 每个版本的固件必须保持 `nvs` 数据格式向前兼容，数据格式变化时需要提供迁移。
- OTA 期间同一网络中会出现不同版本的节点，同步报文的版本字段对不认识的版本直接丢弃，升级后版本不一致的节点之间同步不可用。
- 没有固件签名，设备无法验证镜像的来源，只能依赖 OTA 提供方（控制器）可信；镜像哈希和 Matter 文件头摘要都不能证明来源。
- 回退由引导程序执行，引导程序不能通过 OTA 更新：第一次烧录起就要使用开启回退的引导程序，已经烧录了未开启回退的板子，需要通过烧录插座重新烧录引导程序才有回退能力。
- 固件需要实现自检和确认逻辑，自检的具体项目和超时时间由实现确定；自检只覆盖硬件和启动，发现不了运行中的协议逻辑错误。
- 版本号来自编译机器的本地时钟，不含时区，精度为小时：在时钟不准或时区不同的机器上编译的固件，比较结果可能与实际先后不符；同一小时内编译出的两个固件之间无法升级，被回退固件修复后如果仍在同一小时内构建，也会因版本号相同被拒绝，需要等到下一个小时；到 2100 年版本号回绕，需要换格式。
- Matter SDK 的 OTA 请求端自带“提议的软件版本号必须大于当前软件版本号”的检查，项目不改动它，被回退固件的版本号检查在此之外追加。
- 设备拒绝升级版本号不大于被回退固件的提议，但控制器仍可能再次下发，设备每次拒绝，不下载；只记录最近一次回退的固件，更早回退过的版本不在记录里；恢复出厂设置清除 `nvs`，记录随之清除。
- 测试需要覆盖：自检失败时回退、启动即崩溃时回退、正常固件通过自检并确认、回退后再次收到相同或更低版本号的提议被拒绝、更高版本号的提议仍可升级。
- 使用 `fctry` 之前，开发板需要先烧录测试用的出厂镜像，否则无法配网。
